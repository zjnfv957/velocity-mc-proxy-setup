# MC群组服搭建：一台游戏云VPS跑通Velocity代理与多子服，含配置要点、端口映射与预算核算

单开一个服务器，二十个人进去就开始掉 TPS；宣发拉来的人想玩生存，老玩家只想打小游戏，两拨人在同一个世界里互相膈应。到了这一步，你要的不是"再优化一下服务端"，而是把服务器拆成好几个，前面加一层代理统一对外——这就是群组服。

MC群组服搭建的难点从来不在敲命令。真正让人卡住的是三件事：代理选哪个、这台机器够不够跑好几个进程、以及端口和转发怎么配才不会被玩家投诉"连不上"。下面按这个顺序拆开讲。

## 群组服到底解决什么问题

代理服（Velocity / BungeeCord）本身不跑游戏逻辑，它只做一件事：玩家连代理的地址，代理把人转到对应的子服。

拆开之后有三个直接好处：

- **单服人数天花板被抬高了。** 一个子服卡在几百人，拆成三个各承一部分，总人数就上去了。
- **玩法互不干扰。** 生存服的红石机器卡不到小游戏服，模组服的报错也不会带着大厅一起崩。
- **容灾。** 一个小游戏实例炸了，代理把玩家踢回大厅，其他子服照常运行。

反过来说，如果你只有二十来个朋友一起玩原版生存，群组服是纯粹的额外复杂度。代理层加配置成本，收益基本为零。这层架构适合的是"已经有好几种玩法、或者人数开始撑不住单端"的阶段。

## Velocity 还是 BungeeCord

两个都能用，但新开的网络没有理由选后者。

| 维度 | Velocity | BungeeCord |
| --- | --- | --- |
| 维护方 | PaperMC 团队 | SpigotMC |
| 配置文件 | TOML（`velocity.toml`） | YAML（`config.yml`） |
| 转发机制 | 支持 Modern 转发（共享密钥）+ Legacy | 以 IP forwarding / Legacy 为主 |
| 插件生态 | 现代 API，生态持续增长 | 老牌，历史插件数量大 |
| 资源占用 | 较低 | 相对更高 |
| 适合场景 | 新开网络、子服跑 Paper 系 | 已有强依赖 BungeeCord 插件的老网络 |

关键差别在转发机制。Velocity 的 Modern forwarding 用一份共享密钥校验来连接子服，比传统的 IP 白名单式转发更难被伪造，Paper 1.13 之后的版本原生支持。代价是两边 API 不通用：为 BungeeCord 写的插件不能直接丢进 Velocity。

所以判断标准很简单——你手上没有非它不可的老插件，就用 Velocity。

## 先算清资源账，再下单

群组服最容易被低估的部分是内存。很多人心里想的是"我开个生存服 4G 够了"，然后按 4G 下单，结果代理、大厅、生存、小游戏四个进程一起跑，机器直接开始 OOM 杀进程。

正确的算法是把所有进程的堆内存加起来，再加系统本身的开销：

- **代理进程**：1~2G 内存足够，吃的是连接转发，不是游戏逻辑。
- **大厅 / 登录服**：1~2G。世界小、插件少，别浪费资源。
- **生存 / 生电服**：4~8G 起步，取决于视距和实体数量。
- **模组服或整合包服**：8G 以上，200 个模组级别的整合包会很吃内存。

举个具体的组合：代理 + 大厅 + 生存 + 一个小游戏服，按上面中位数估就是 2+2+6+4 = 14G 左右的堆内存需求。这意味着 4核8G 这种"单服很舒服"的配置，在群组服场景下是不够的。

CPU 这边，MC 服务端主线程基本是单线程工作，**单核主频比核心数更重要**。高主频机型在同样人数下的 TPS 表现，通常好过低频多核。带宽方面，代理是所有玩家流量的汇聚点，原版端一个玩家大致在 1~1.5Mbps 量级，按峰值人数往上留余量。

## MC群组服搭建实操：从端口到启动

### 第一步：规划端口和映射

先定好每个进程的端口，写在纸上比事后翻配置文件强：


代理 Velocity        25565  ← 唯一需要对外映射的端口
大厅 lobby           25566
生存 survival        25567
小游戏 minigame      25568


子服只绑定内网地址或者说本机地址，不要单独做端口映射。在雨云控制台的 NAT 端口映射里，只把代理那一个端口映射到公网即可。基岩版走 UDP 19132，和 Java 版是两套入口。

### 第二步：配置每个子服

不管用 Paper 还是 Purpur，子服的 `server.properties` 里都要设：

properties
online-mode=false


正版验证由代理统一做，子服自己再验一次，玩家就进不来。

然后是转发配置，两条路线二选一：

- **Velocity Modern 转发**：在 `paper-global.yml` 里把 `proxies.velocity.enabled` 设为 `true`，`online-mode` 保持 `true`，`secret` 填的内容必须和代理端 `forwarding.secret` 文件里的字符串完全一致。
- **BungeeCord 兼容模式**：在子服开启 `bungeecord: true`（新版 Paper 在 `paper-global.yml` 的 `proxies.bungee-cord` 段），代理端用 legacy 转发。

两边密钥对不上，是最常见的"配置看起来全对但就是进不去"的原因。

### 第三步：配置代理端

Velocity 首次启动会生成 `velocity.toml`，要改的核心就三块：

toml
bind = "0.0.0.0:25565"

[servers]
lobby = "127.0.0.1:25566"
survival = "127.0.0.1:25567"
minigame = "127.0.0.1:25568"
try = ["lobby"]

[forced-hosts]
# 需要的话，用不同域名指向不同子服


`try` 决定玩家第一次进来落到哪个服，一般填大厅。

### 第四步：启动顺序和验证

**先起子服，再起代理。** 代理启动时会尝试连接配置里的子服，子服没起来会一直报连接失败。

验证环节分三次：先用 `/server survival` 确认能手动跳转；再断开重连，确认能自动落到大厅；最后在子服控制台确认玩家 IP 显示的是真实公网 IP 而不是 `127.0.0.1`——后者说明转发没生效。

Java 版本别搞错：1.17 以上服务端要 Java 17，1.20.5 之后部分版本要 Java 21，Velocity 3.x 同样是 Java 17 起步。用 Docker 或者 MCSManager 面板的话，可以直接建多个不同 JDK 版本的环境镜像，切换版本时会轻松很多。

## 跨服数据怎么打通

拆成多服之后，子服之间默认是数据隔离的：玩家在生存服攒的金币，到小游戏服就是零。想打通，最省事的是共享数据库方案——所有子服连同一个 MySQL，玩家数据按 UUID 存，任何一个子服都能读写。

权限插件（LuckPerms 之类）建议也走同一个数据库，或者干脆装在代理层统一管理。用代理层管权限，好处是玩家在任意子服切换时权限即时生效；缺点是代理重启会影响全局，看你更在意哪一头。

实时性的东西，比如"玩家现在在哪个子服""跨服传送通知"，用代理的插件消息通道更合适。它适合做通知，不适合当主存储。

## 几个高频踩坑

**"你已在其他服务器登录"** 多数是子服的 `online-mode` 没关，或者转发密钥不一致，导致同一个 UUID 被当成两个玩家。

**子服被绕过代理直连** 检查是否给子服单独做了端口映射。群组服场景下子服端口对外基本没有正当理由。

**人数一多就掉 TPS** 先看是哪个子服在掉。代理层很少成为瓶颈，真正的限制一般出现在某个子服的单核性能或内存上。

**内存算漏了** 四个进程各自 4G 堆内存，机器只有 12G，必然触发 OOM Killer 随机杀进程，表现出来就是"服务器莫名其妙没了"。

**动态计费账单比预期高** 群组服是常驻负载，动态计费的电量费会持续累加。开服前先按固定计费算一遍总价。

## 常见问题

**群组服一定要用独立服务器吗？**
不一定。代理层很轻，一台配置够的 VPS 完全可以承载整个网络。只有当子服数量多到单机内存装不下时，才需要考虑拆机器——雨云的产品支持内网互通，跨机器组网也是可行路线。

**我能不能先用最低配试一下？**
可以，而且建议这么做。代理 + 大厅 + 一个小游戏服的最小组合，入门级配置就能跑起来，把配置和转发流程先验证通，再按实际人数升级。游戏云支持随时升级配置，也支持 1 元试用一天。

**面板服和 VPS 到底选哪个？**
完全不想碰命令行、只开一个服，选面板服。要做群组服，选 VPS。
